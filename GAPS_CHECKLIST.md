# Gaps Checklist — e-learning-platform

Generated by reading: `backend/index.js`, all files in `src/components/`, `App.jsx`, `main.jsx`, both `package.json`, `README.md`. Ordered cheapest-first within each tier. Nothing here has been fixed yet — check items off as Phase 2 completes them.

## Tier 1 — Security / correctness bugs (fix regardless of interview use)

- [x] **Debug endpoints exposed with no guard** — `/db-test` and `/debug-db` (`backend/index.js:102-118`) leak `current_database()`/`current_user` and server time to any caller, no auth, no environment check.
  *Why it matters:* an interviewer who pokes at your API with curl will find these in 10 seconds and ask "would this be in prod?" Dead giveaway of unfinished hardening.
  *Effort:* 5 min — delete or wrap in `if (process.env.NODE_ENV !== "production")`.

- [ ] **Login/register return the full DB row, including the bcrypt hash** — `backend/index.js:95` (`return res.json({ success: true, user })`) sends the entire `users` row straight from `SELECT *`, hash and all, and the frontend stores it verbatim in `localStorage` (`auth.jsx:33,48`).
  *Why it matters:* classic "explain your auth design" interview trap — you'd have to admit the password hash sits in the browser's localStorage indefinitely, readable by any XSS or browser extension. This is the single most-asked-about line in a codebase like this.
  *Effort:* 10-15 min — `SELECT` only needed columns, or strip `password` before responding.

- [x] **Hardcoded DB credentials committed to source** — `backend/index.js:23-29` (`password: "redBERRY123/"`), no `.env`, no `dotenv` dependency despite `.gitignore` already listing `.env`.
  *Why it matters:* "how do you manage secrets/config across environments" is a standard fresher question; right now the answer is "I don't." Also the password is sitting in git history right now.
  *Effort:* 15-20 min — add `dotenv`, move to `.env` (already gitignored), update README setup steps.

- [x] **API error responses leak raw DB error messages** — every route (`/courses`, `/login`, `/db-test`, `/add-course`) does `res.json({ success:false, error: err.message })`, exposing internal error text (which can include table/column names) to the client.
  *Why it matters:* information disclosure — a reviewer will ask "what happens if the DB is down / a constraint fails" and the honest answer is "the client sees your schema internals."
  *Effort:* 15 min — log `err` server-side, return a generic message to the client.

- [x] **`/add-course` writes to a table that doesn't match the read path (`course` vs `courses`)** — `GET /courses` (`index.js:37-49`) reads from `course` (singular, per README schema: `title, description, duration_weeks, instructor_id`), but `POST /add-course` (`index.js:120-133`) inserts into `courses` (plural) with columns `title, instructor, price` that don't exist on the documented schema at all.
  *Why it matters:* this endpoint is either dead code that errors on every call or is quietly writing into an entirely different, undocumented table — either way it's evidence the "Course Management" resume bullet was never actually exercised end-to-end.
  *Effort:* 20-30 min — fix the table/columns to match the real schema, or delete the endpoint if course creation isn't a real feature yet.

- [x] **No input validation on `/register` / `/login`** — empty strings, malformed emails, and missing fields are all passed straight to `bcrypt.hash`/the query with no checks.
  *Why it matters:* baseline expectation for any auth endpoint; easy to demo breaking it live in an interview ("what happens if I POST an empty body?" → 500 or silent garbage row).
  *Effort:* 30 min — basic presence/format checks, return 400 with a clear message.

- [x] **No rate limiting on `/login` or `/register`** — unlimited attempts, no lockout, no delay.
  *Why it matters:* "how would you prevent brute-forcing this login" is a common follow-up once they see bcrypt is used correctly elsewhere; right now there's no answer.
  *Effort:* 30 min — `express-rate-limit` on the two auth routes.

- [ ] **No auth/session check on any route** — `/add-course` (and any future mutating route) is completely unauthenticated; "login" only ever produces a plain object stored in `localStorage`, never validated again by the server. `jsonwebtoken` is a listed dependency and imported (`index.js:52`) but **never used anywhere** — no token is signed, issued, or verified.
  *Why it matters:* this is the gap most likely to surface directly in an interview if the resume mentions JWT/session-based auth anywhere — right now there is no server-side session concept at all, just an honor-system client object. Also means anyone can call `/add-course` without logging in.
  *Effort:* 1-2 hrs — sign a JWT on login/register, add an `authenticate` middleware, protect mutating routes, send token via `Authorization` header instead of raw user object.

## Tier 2 — Gaps between resume claims and actual behavior

- [ ] **"Recommended for you" is a hardcoded array** — `Dashboard.jsx:58-63` ships four fixed courses (AWS, React, Data Science, UI/UX) with fake prices, completely disconnected from the database.
  *Why it matters:* the cheapest fake-data item to defend badly — if asked "how does recommendation work" the honest answer is currently "it doesn't, it's a literal.” Turning it into even a simple "other courses not yet enrolled in" query removes that.
  *Effort:* 30-45 min — replace with a real query (e.g. courses excluding the ones the user's enrolled in).

- [ ] **"Lesson X of Y" is a hardcoded fallback, not real data** — `CourseCard.jsx:30` (`Lesson {lessonsDone || 5} of {totalLessons || 7}`) — every caller passes `0`/`0`, which the `||` silently replaces with fake `5`/`7`, even though the DB schema already has a `module` table this could be `COUNT`-ed from.
  *Why it matters:* this is the kind of hardcoded number that's very easy for an interviewer to spot by opening dev tools and comparing two different courses that show identical "5 of 7" lesson counts.
  *Effort:* 45 min-1 hr — add a module-count query/join to `/courses`, pass real numbers through.

- [ ] **Category browsing has no backing data** — `Dashboard.jsx:51-56` hardcodes 4 categories with lorem-ipsum descriptions; every course from the DB is force-labeled `"General"` on the frontend (`Dashboard.jsx:37`, `AllCourses.jsx:21`, `coursessection.jsx:35`) because the `course` table has no category column at all.
  *Why it matters:* the UI implies filterable categories but there's no schema support for it — if asked to filter by "Design" live, nothing would happen. Either the schema needs a column or this claim should quietly become "category cards" (marketing) not "category filtering" (feature).
  *Effort:* 1-1.5 hrs — add a `category` column to `course` (or a join table), wire real filtering on `/courses`.

- [ ] **Progress tracking is entirely fake — the headline resume gap.** `Dashboard.jsx:36` hardcodes `progress: 60` for every course; `AllCourses.jsx:18` hardcodes `progress: 0`. There is no `/enroll` endpoint, no read/write of the `enrollment` table anywhere in `backend/index.js`, and the "in-progress courses" section on the Dashboard actually renders **all courses in the DB**, not courses the user enrolled in — there's no concept of enrollment on the client or server at all, despite the schema already having `enrollment(user_id, course_id, progress_percent)`.
  *Why it matters:* if the resume says anything like "personalized dashboard with progress tracking" or "enrollment tracking," this is the line item that gets exposed the moment someone asks "walk me through what happens when a user enrolls in a course" — right now nothing happens, there is no enroll action anywhere in the UI.
  *Effort:* 2-4 hrs — add `POST /enroll`, add an enroll button/flow, add `GET /my-courses` that joins `enrollment` to `course` for the logged-in user, replace the hardcoded arrays with real data.

## Tier 3 — Real but lower-priority engineering gaps

- [x] **`LandingPage.jsx:10-13` navigation stub does nothing but `console.log`** — `handleNavigate` is passed to `Header` as `onNavigate` but never actually called by anything meaningful; dead code left mid-refactor.
  *Why it matters:* minor, but "why is this here" is an easy question to fumble if you haven't looked at the file in a while.
  *Effort:* 5 min — delete the unused prop/handler.

- [x] **Footer links are all `href="#"`** — `footer.jsx:16-40`, `Dashboard.jsx` footer section — cosmetic dead links.
  *Why it matters:* low — only matters if someone clicks around during a demo.
  *Effort:* 5-10 min — either real anchors or remove the links.

- [x] **Duplicate `CourseCard` components with diverged styling approaches** — `src/components/courses/CourseCard.jsx` (CSS classes) and `src/components/landing/coursecard.jsx` (inline style objects) are near-identical but maintained separately.
  *Why it matters:* "why are there two of these" is an easy avoidable question; also a real maintenance smell (fix a bug in one, forget the other — already slightly diverged).
  *Effort:* 20-30 min — consolidate into one shared component.

- [ ] **Duplicate `Header` components with inconsistent auth-awareness** — `src/components/header/Header.jsx` checks `localStorage` and swaps Login/Signup for Logout; `src/components/landing/headerLanding.jsx` always shows Login/Signup regardless of auth state.
  *Why it matters:* actual bug a reviewer can trigger by logging in then visiting `/` — the landing page header will still show "Login/Sign Up" for a logged-in user.
  *Effort:* 30 min — consolidate into one header, make it auth-aware everywhere.

- [x] **API base URL (`http://localhost:5000`) hardcoded in four separate files** — `auth.jsx`, `Dashboard.jsx`, `AllCourses.jsx`, `coursessection.jsx` each hardcode the string independently.
  *Why it matters:* "how would you point this at a deployed backend" — right now that's a 4-file find-replace, an obvious sign of no config layer.
  *Effort:* 20 min — single `const API_BASE` (or `.env` + `import.meta.env`), import everywhere.

- [ ] **No shared auth/user state — every component reads `localStorage` ad hoc** — `Header.jsx:9`, `Dashboard.jsx:11-26` each independently `JSON.parse(localStorage.getItem("user"))` with slightly different error handling.
  *Why it matters:* textbook case for "why didn't you use Context here" — reasonable for a fresher project but worth having an answer ready, or just fixing it since it's cheap.
  *Effort:* 45 min-1 hr — a small `AuthContext` + `useAuth()` hook.

- [ ] **Dashboard route "guard" is an imperative full-page redirect, not a route guard** — `Dashboard.jsx:11-26` does `window.location.href = "/login"` inside a `useEffect`, causing a full page reload and a flash of "Loading..." instead of using React Router.
  *Why it matters:* works, but shows unfamiliarity with the router library already in the dependency list (`react-router-dom`).
  *Effort:* 30 min — `<PrivateRoute>` wrapper component using `<Navigate>`.

- [ ] **No pagination anywhere** — `/courses` returns every row unbounded; `AllCourses.jsx` and `coursessection.jsx` render the full/sliced result client-side with no page controls.
  *Why it matters:* fine at demo scale (a handful of seeded courses), but "what happens at 10,000 courses" is a standard scaling question.
  *Effort:* 1-2 hrs — `LIMIT`/`OFFSET` or cursor pagination on the backend, page controls on the frontend.

- [x] **No separation of concerns in the backend — everything lives in one 139-line `index.js`** — routes, DB pool setup, and business logic are all inline with no routes/controllers/db-layer split.
  *Why it matters:* fine for a project this small, but "how would this scale to more routes" is worth having a real answer for beyond "it wouldn't, cleanly."
  *Effort:* 1-2 hrs — split into `routes/`, `controllers/`, `db.js`.

- [ ] **Zero automated tests** — backend `package.json` still has the default `"test": "echo \"Error: no test specified\" && exit 1"` placeholder; no frontend tests either.
  *Why it matters:* almost every fresher interview asks "how did you test this" — even 3-4 backend route tests (register/login happy + failure paths) gives a real, honest answer instead of "I tested manually."
  *Effort:* 2-4 hrs — `jest` + `supertest` for the auth routes at minimum.
